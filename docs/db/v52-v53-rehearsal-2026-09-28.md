# V52·V53 migration 호환·복원 리허설 (2026-09-28)

대상 릴리스: `8f7d60b8b5cdd39102da7c6c8b39c9835b0ea38b`. Document source는 `0b32a3d9c11e4615191f2bf9dd68234bcf83367c`(PR #23), AI source는 `be6cbebbe0ede9f8e76e56035a32694d33489580`(Fruition-ai PR #21)이다.

- `V52__request_wiki_cleanup_for_trashed_documents.sql`: 휴지통 문서마다 `document_deleted` command를 `ai_command_outbox`에 넣는다. 휴지통 편집 문서의 `status`를 `uploaded`로 바꾸고, 그 문서들의 `wiki_page_contributions.active`를 끈다. 스키마 변경은 없는 데이터 migration이다.
- `V53__index_active_contributions_by_source_document.sql`: `wiki_page_contributions(source_document_id) WHERE active` 부분 인덱스를 추가한다.
- AI `ai_schema.sql`: `wiki_source_tombstones` 테이블을 추가한다(`CREATE TABLE IF NOT EXISTS`).

## 방법

1. 격리된 `postgres:16` 컨테이너에서 이 저장소의 Flyway Gradle 설정(`flywayMigrate -Pflyway.target=51`)으로 V1~V51을 적용했다. 운영의 배포 전 스키마와 같고, V36 Java migration도 포함된다.
2. synthetic 데이터를 넣었다.
   - 문서 1,000개: 활성 700(EDITABLE 490, ORIGINAL 210), 휴지통 300(EDITABLE 210, ORIGINAL 90). 상태는 `completed`·`processing`·`failed`·`uploaded`를 섞었다.
   - 편집 문서마다 ingest 작업 로그 1개와 기여 3개(source 1, concept 2): 2,100행 중 105행은 미리 비활성으로 두었다.
   - 무관한 `query` outbox 20행
3. 네 테이블(`documents`, `wiki_page_contributions`, `ai_operation_logs`, `ai_command_outbox`)의 행 checksum을 기록하고 `pg_dump -Fc`로 백업했다.
4. `flywayMigrate`로 V52·V53을 적용하고 결과와 구·신 버전 SQL을 확인했다.
5. 백업을 새 DB에 `pg_restore`해 checksum을 비교하고, 복원본에 V52·V53을 다시 적용했다.
6. AI DB: 이전 `main`(`ab064d3`)의 `ai_schema.sql`에 wiki page 200행을 넣고 백업했다. 새 `ai_schema.sql`을 두 번 적용한 뒤 백업을 복원해 비교했다.

## 판단

- expand-only. V52는 스키마를 바꾸지 않는다. 구버전 코드는 비활성 기여를 원래 복구 대상에서 제외하고 휴지통 문서의 `status`를 쓰지 않으므로, 롤링 중 구·신 버전이 같은 DB를 써도 된다. V53과 AI tombstone 테이블은 추가 전용이다.
- V52의 데이터 변경(정리 command 발행, 휴지통 편집 문서 상태 초기화, 기여 비활성화)은 **이미지 롤백으로 되돌아가지 않는다.** 되돌리려면 배포 전 백업이나 시점 복원이 필요하다. 이미 휴지통에 있던 문서는 운영상 복구 뒤 다시 편입하면 되므로 롤백 시 데이터 복원은 필요하지 않다고 판단했다.
- V53의 `CREATE INDEX`는 Flyway 트랜잭션 안이라 `CONCURRENTLY`를 쓸 수 없다. 인덱스를 만드는 동안 `wiki_page_contributions` 쓰기가 잠시 막히지만, 합성 2,100행에서 2ms였다.

## 범위 제한

synthetic 데이터로 검증했다. 운영 데이터 규모의 lock·소요 시간, RDS 자동 백업·PITR 복원, 구·신 애플리케이션 업무 흐름의 동시 실행, V52 command를 AI ingest worker가 실제로 처리하는 과정은 포함하지 않는다. 전체 스키마와 삭제·폴더 삭제·편입 중 삭제 시나리오는 `./gradlew test`의 Testcontainers 통합 테스트(PR #18, 901 tests)에서 따로 확인했다.
