## 방법

1. 격리된 `postgres:16`에 Platform의 `infra/postgres/init-db-isolation.sh`를 그대로 실행했다(`DB_ISOLATION_TARGET=core`). 운영과 같이 migration role(`core_migration`, `ai_migration`)과 runtime role(`core_runtime`, `ai_runtime`)을 분리하고 default privileges를 설정한다.
2. `core_migration`으로 이 저장소의 Flyway Gradle 설정(`flywayMigrate -Pflyway.target=50`)을 실행해 운영과 같은 V50 스키마를 만들었다. V36 Java migration도 포함된다.
3. `core_runtime`으로 synthetic 데이터를 넣었다.
   - 폴더 80개(루트 20, 하위 60)
   - 문서 1,001개: 루트·폴더에 분산. 휴지통 300개(편집 210, 원본 90). 휴지통 문서와 이름이 같은 활성 문서 1개
   - 편집 문서의 ingest 작업 로그와 기여 2,103행. 일부는 미리 비활성으로 두었다
   - 무관한 `query` outbox 20행
4. V51 문서의 **사전 충돌 조회 SQL**을 실행했다. 다섯 테이블의 행 checksum을 기록하고 `pg_dump -Fc`로 백업했다.
5. `core_migration`으로 `flywayMigrate`를 실행해 V51~V53을 한 번에 적용했다. 결과를 확인하고, `core_runtime`으로 앱이 쓰는 쓰기 SQL을 실행했다.
6. 백업을 새 DB에 복원해 checksum을 비교했다. 복원본에 V51~V53을 다시 적용했다.
7. **실패 경로:** 다른 복원본에 같은 부모의 파일·폴더 이름 충돌(`d3.md` 파일과 `D3.md` 폴더)을 만들었다. 사전 조회가 이를 잡는지, V51이 실패할 때 원상태로 남는지 확인했다.
8. AI DB: 운영 AI `c6a0308`의 `ai_schema.sql`을 `ai_migration`으로 적용하고, `ai_runtime`으로 wiki page 200행을 넣어 백업했다. 새 `ai_schema.sql`을 `ai_migration`으로 두 번 적용한 뒤 runtime 권한과 쓰기, 백업 복원을 확인했다.

## 판단

- 스키마는 추가 전용이다. V51은 기존 고유 인덱스를 **완화**(workspace 전체 → 부모별)하고 새 테이블·트리거를 추가한다. V52는 데이터만 바꾸고 V53·AI 테이블은 추가만 한다. 구버전 코드가 쓰는 SQL은 새 스키마에서 동작한다.
- **배포 전 운영 DB에서 V51 사전 충돌 조회를 반드시 실행한다.** 결과가 있으면 V51이 실패해 배포가 중단된다. 데이터는 원상태로 남는다. 충돌 항목은 사람이 정리한 뒤 다시 배포한다.
- V51은 `documents`·`folders`에 쓰기 잠금을 잡고 backfill한다. 합성 781행에서 8ms였고, 운영 규모에서는 그 시간만큼 이름 쓰기가 막힌다.
- **롤백 주의:**
  - V52의 데이터 변경(정리 command, 휴지통 편집 문서 상태 초기화, 기여 비활성화)은 이미지 롤백으로 되돌아가지 않는다.
  - V51 이후 다른 폴더에 같은 이름이 생기면 V48의 전역 고유 인덱스로 단순 복원할 수 없다.
  - 되돌리려면 배포 전 백업이나 시점 복원이 필요하다.

## 범위 제한

synthetic 데이터로 검증했다. 운영 데이터 규모의 잠금·소요 시간, 운영 데이터의 실제 이름 충돌 여부(사전 조회는 운영에서 실행해야 함), RDS 자동 백업·PITR 복원, 구·신 애플리케이션 업무 흐름의 동시 실행, V52 command를 AI ingest worker가 실제로 처리하는 과정은 포함하지 않는다. 전체 스키마와 삭제 시나리오는 `./gradlew test`의 Testcontainers 통합 테스트(PR #18, 901 tests)에서 따로 확인했다.
