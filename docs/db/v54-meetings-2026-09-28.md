# 회의 실시간 받아쓰기 V54 배포 검증

## 변경

> 번호 변경: 처음 `V52__add_meetings.sql`로 만들고 아래 검증을 V51 위에서 했다. 이후 dev에 `V52__request_wiki_cleanup_for_trashed_documents`, `V53__index_active_contributions_by_source_document`가 들어와 번호가 겹쳐, 내용은 그대로 두고 **V54**로 옮겼다. 아래 표의 V52는 당시 번호다. 새 번호로 dev(V53) 위에서 다시 확인한 결과는 문서 끝 "번호 변경 후 재검증"에 있다.

`V54__add_meetings.sql`은 `meetings`, `meeting_streams`, `meeting_segments` 세 테이블과 인덱스 두 개를 새로 만든다. 기존 테이블을 변경·잠금하지 않고 backfill도 없다(`migration_mode: expand-only`). 이전 버전 앱은 새 테이블을 읽거나 쓰지 않는다. 계약과 설계는 [Meetings API](../api/meetings.md), [ADR-0023](../adr/0023-meeting-transcripts-and-recordings.md)을 따른다.

## 배포 제약

- migration/runtime role을 분리한 배포에서는 runtime role(`core_runtime`)에 새 테이블 SELECT/INSERT/UPDATE/DELETE 권한이 필요하다. 로컬 검증에서는 platform `init-db-isolation.sh`의 default privileges로 자동 부여됐다. 운영 DB도 같은 default privileges인지 적용 전에 확인한다.
- 새 앱은 WebSocket 경로(`/api/meetings/*/live`)와 `SPEECH_LIVE_ENDPOINT` 설정이 필요하다. ALB·Vercel 경로는 platform ADR-0022를 따른다.
- 롤백: 이전 버전 앱은 이 마이그레이션이 적용된 DB에서 그대로 동작한다(아래 검증). 테이블 삭제가 필요하면 회의 데이터(개인정보)를 먼저 처리한 뒤 별도 릴리스로 수행한다.

## 로컬 호환성 검증 (2026-09-28)

개발 DB·Redis는 사용하지 않았다. 별도 컨테이너를 만들었다.

- PostgreSQL 16: `fruition-v52-postgres`, 127.0.0.1:15433. platform `init-db-isolation.sh`로 `core_migration`·`core_runtime` 분리.
- Redis 7: 127.0.0.1:16379
- MinIO: 127.0.0.1:19000

Kafka는 연결하지 않았다(outbox 발행은 재시도 상태로 남음).

| 순서 | 대상 | 결과 |
|---|---|---|
| 1 | 이전 버전(`origin/dev` `ad76afe`) `--migrate-only` | V1~V51 적용 |
| 2 | 이전 버전 앱으로 기존 데이터 생성 | 폴더 생성 201, Markdown 문서 생성 201, 목록·트리 200, 채팅 세션 201, 본문 저장(revision 2) 200 |
| 3 | 새 버전 `--migrate-only` | V52 success, 실행 22ms. `core_runtime`에 세 테이블 DELETE·INSERT·SELECT·UPDATE 권한 확인. 기존 문서·편집 상태 행 유지 |
| 4 | 새 버전 앱 | 기존 데이터: 목록 200(문서 1건), 트리 200, 본문 저장(revision 3) 200 |
| 5 | 새 버전 앱 — 회의 API | 기존 문서를 대상으로 회의 생성 201, 같은 Idempotency-Key 재요청 시 같은 회의 반환, 조회 200, 다른 사용자 조회 404(`MEETING_NOT_FOUND`), ticket 발급 200 |
| 6 | 새 버전 앱 — WebSocket | ticket 접속 성공 후 AI 연결 실패를 `transcription_failed`·close 1011로 전달, 연결 `failed` 기록, 잠금 해제(`live_connected=false`). 같은 ticket 재사용은 HTTP 401 |
| 6-1 | 새 버전 앱 — 실제 AI 연결 | 로컬 ai-svc(`localhost:8000`, 실제 OpenAI 모델)와 access(8081)의 실제 OWNER 멤버십으로 접속. 한국어 합성 음성 2문장(각 약 2.9초, 24 kHz PCM16, 0.5초 조각을 실시간 속도로 전송)을 보내 `ready`(3.5초) → `delta` → `committed`(position 1, 2) → `completed` 2건 → `finished`(segment_count 2) 수신. 조회 결과 두 문장이 순서대로 저장, `end_reason=finished`, `transcript_complete=true` |
| 7 | 롤백: V52 DB에서 이전 버전 앱 | 기동 정상(Flyway 검증 오류 없음), 목록 200, 본문 저장(revision 4) 200. 회의 API는 없음(404) |

6단계는 검증용 내부 토큰이 로컬 AI와 달라 AI가 handshake를 401로 거절한 조건이다. 6-1단계는 로컬 AI의 내부 토큰으로 다시 연결했다(토큰 값은 기록하지 않음). 실제 연결에서 확인한 사항:

- `delta`가 해당 구간의 `committed`보다 먼저 온다. 순서는 `committed`의 position으로만 정하므로 저장 결과에는 영향이 없다. 클라이언트는 position이 없는 구간의 delta를 마지막 줄에 임시로 표시해야 한다.
- 접속 후 `ready`까지 약 3.5초(AI 연결·모델 설정). 말을 시작하고 첫 delta까지 약 1.2초.
- AI가 호출하는 access는 로컬 8081 인스턴스이며 5433 PostgreSQL의 access_db를 쓴다. 멤버십은 읽기만 했고 회의 데이터는 격리 DB에만 저장했다.

AWS 경로(ALB·WAF·Vercel)는 이 검증에 포함하지 않았다. 전사 순서·충돌·종료 대조는 가짜 AI WebSocket 통합 테스트(`MeetingLiveIntegrationTest`)로 검증했다.
