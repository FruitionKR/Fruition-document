# V50 migration 호환·복원 리허설 (2026-09-21)

대상: `V50__checkpoint_pdf_conversion_batches.sql` (source `1ddf5b9f416fb60d8834ae29cd23c68ba2e6c487`, PR #8)

```sql
ALTER TABLE document_convert_queue
    ADD COLUMN completed_pages integer NOT NULL DEFAULT 0,
    ADD COLUMN total_pages integer NOT NULL DEFAULT 0,
    ADD COLUMN attempts integer NOT NULL DEFAULT 0,
    ADD COLUMN updated_at timestamptz NOT NULL DEFAULT now(),
    ADD COLUMN next_attempt_at timestamptz NOT NULL DEFAULT now();
CREATE INDEX ix_document_convert_queue_claim ON document_convert_queue(status, next_attempt_at, created_at);
```

## 방법

격리된 `postgres:16` 컨테이너(`--network none`)에 현재 릴리스의 `document_convert_queue` 열(id, document_id, source_document_id, created_at, status)만 가진 synthetic 테이블을 만들고 1,000행(일부 `processing`)을 넣은 뒤 `lock_timeout=2s`, `statement_timeout=10s`로 V50 SQL을 그대로 실행했다. 이후 `pg_dump` → 새 DB restore → 행 checksum을 비교했다.

## 판단

- expand-only. 상수 DEFAULT의 `ADD COLUMN`은 PostgreSQL 11+에서 테이블 재작성 없이 카탈로그만 갱신한다. `CREATE INDEX`는 Flyway 트랜잭션 안이라 `CONCURRENTLY`를 쓸 수 없고 SHARE lock으로 쓰기를 잠시 막지만 대상은 작은 큐 테이블이다.
- 구 이미지 document-svc는 새 열을 몰라도 INSERT/SELECT가 동작한다. 신 이미지는 V50 없이는 기동하지 않으므로 migration Job 이후에 배포한다.
- 롤백 시 열·인덱스를 제거할 필요가 없다.

## 범위 제한

단일 synthetic 테이블만 검증했다. Flyway 실행과 전체 스키마(V1~V50)는 `./gradlew test`의 testcontainers PostgreSQL 통합 테스트(886 tests)에서 별도로 적용·확인했다. 운영 lock/부하, RDS PITR, 구/신 애플리케이션 업무 흐름의 동시 실행은 이 리허설에 포함되지 않는다.
