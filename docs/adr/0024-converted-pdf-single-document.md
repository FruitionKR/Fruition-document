# ADR-0024: PDF 변환 결과를 문서 하나로 저장

- 상태: 채택 (2026-10-23 단일 문서 보장으로 수정)
- 관련: [ADR-0016](0016-consolidate-document-body-into-postgres.md), [ADR-0015 Markdown 변환기](https://github.com/FruitionKR/Fruition-ai/blob/main/docs/adr/0015-markdown-converter.md)

## 맥락

AWS 모드의 PDF 변환은 converter `POST /convert-source-batch`로 10페이지씩 변환한다. 기존 구현은 묶음 결과를 UTF-8 64KiB 단위로 잘라 첫 조각만 원본 문서에 넣고, 나머지는 `origin=convert_part` 문서로 따로 만들었다. 변환이 끝나면 파트마다 AI 큐에 등록했다.

이 방식에는 세 가지 문제가 있었다.

- PDF 한 편이 여러 위키 소스로 편입된다. 파트를 넘는 맥락이 끊기고 소스 노드가 흩어져 지식 그래프가 쪼개진다.
- 64KiB 경계가 표나 수식 블록 중간을 자를 수 있다. 헤더가 없는 표 조각과 닫히지 않은 `$$`가 생겨 화면에서 깨진다.
- converter는 묶음 PDF를 독립 문서로 처리해 묶음마다 `<!-- page 1 -->`부터 다시 센다.

## 결정

1. PDF 한 편의 변환 결과는 크기에 관계없이 하나의 문서에 저장한다. 5MB를 넘는다는 이유로 파트 문서를 만들거나 본문을 버리지 않는다.
2. converter의 내부 페이지 묶음은 처리 단위일 뿐이다. 첫 묶음은 placeholder를 대체하고 이후 묶음은 같은 문서에 원본 페이지 순서대로 이어 붙인다.
3. 묶음의 페이지 주석을 원본 PDF 기준 번호로 바꿔 저장한다.
4. 저장소 revision CAS와 큐 checkpoint로 재전송·순서 역전 시 중복 저장을 방지한다. 변환 중에는 사용자·Agent 저장을 거절한다.
5. 직접 Markdown 생성·업로드의 5MB 제한을 변환 결과나 기존 문서의 저장·복제·복원·편집 상태 초기화에 적용하지 않는다. HTTP 요청과 이미지의 전송 제한은 별도 유지한다.
6. 최종 버전 기록과 AI 인제스트는 문서 단위로 수행한다. 과거 버전에서 생성한 파트의 처리 호환성은 유지한다.

## 대안과 기각 사유

- **5MB 초과 시 문서 분리:** 사용자가 전체 내용을 한 문서에서 확인할 수 없고, 위키 소스와 문맥이 분리된다.
- **화면에서만 파트를 이어 보여주기:** 실제 문서와 위키 소스가 여러 개로 남는다.
- **묶음마다 버전 기록:** 누적 본문이 버전마다 복제되어 저장량이 과도하게 늘어난다.

## 결과와 남은 제약

- 새 변환 결과에는 크기 때문에 생기는 파트 제목이 붙지 않는다. 모든 페이지가 같은 문서 ID에 저장된다.
- 이미 분리되어 저장된 기존 문서는 자동 삭제하거나 합치지 않는다. 기존 편집 내용 보존을 확인한 별도 통합 작업이 필요하다.
- 큰 본문의 저장·렌더링 비용은 남는다. 과거 에디터 측정에서 5MB 로딩 약 15초, 10MB 키 입력 4~7초가 관찰되었다. 성능 개선은 문서 분리가 아닌 내부 처리·렌더링 방식으로 해결해야 한다.
- 요청 전송 한도보다 큰 본문의 브라우저 저장은 별도 전송 개선이 필요하다. 이 제한 때문에 서버 변환 결과를 분리하지는 않는다.
- 로컬 모드의 전체 PDF 변환 경로 역시 문서 하나를 유지한다.
