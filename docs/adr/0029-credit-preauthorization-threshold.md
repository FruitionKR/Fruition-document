# ADR-0029: 크레딧 사전 승인 기준

- 상태: 결정됨, 구현 예정 ([#102](https://github.com/FruitionKR/Fruition-document/issues/102))
- 관련: [#79](https://github.com/FruitionKR/Fruition-document/issues/79), [ADR-0026](0026-credit-payments.md), [ADR-0027](0027-ai-usage-billing-and-price-management.md)

## 맥락

`CreditService`는 AI 요청 전에 계정 행을 잠그고 요청 종류별 예상 상한(`app.billing.estimate.<kind>`)을 예약한다. 끝나면 실제 청구액으로 정산하고 예약을 푼다. 실제 금액이 예약보다 크면 그대로 차감하므로 잔액은 마이너스가 될 수 있다(의도된 동작).

`app.billing.enforce`(`BILLING_ENFORCE`)가 true일 때만 거절하는데 기본값이 false이고 배포 설정에도 없어서, 운영에서도 잔액이 0이나 마이너스여도 AI 요청이 실행된다. 개발자가 실제 공급사 API로 테스트하는 단계라 꺼 둔 것이지만, 실사용자를 받기 전에 거절 기준을 정해야 한다.

전제는 이미 정했다. 잔액이 0 이하면 새 요청을 거절한다. 요청을 시작한 뒤 토큰을 얼마나 쓸지는 미리 알 수 없으므로 진행 중인 요청은 끝까지 실행하고 실제 비용만큼 차감한다. 남은 질문은 "가용 잔액이 얼마 이상이어야 통과시키는가"와 "얼마를 예약하는가"다.

## 결정

1. **거절 기준은 그 요청 종류의 최저 비용이다.** 가용 잔액(잔액 − 진행 중인 예약)이 요청 종류의 최저 비용보다 작을 때만 거절한다. 최저 비용은 종류별 설정값 `app.billing.minimum.<kind>`로 둔다. 초기값은 기본 모델로 가장 짧은 요청을 보냈을 때의 비용이고, 과금 정확성 작업([ADR-0027](0027-ai-usage-billing-and-price-management.md)) 뒤 원장의 실제 최저 청구액(예: 하위 5% 값)을 보고 조정한다.
2. **예약 금액은 종류별 예상 상한을 유지하되 가용 잔액을 넘지 않는다.** 가용 잔액이 상한보다 작으면 가용 잔액만큼만 예약한다. 진행 중인 요청의 예약이 가용 잔액을 줄여 동시 요청을 자연스럽게 제한한다.
3. **정산은 그대로 둔다.** 진행 중인 요청은 끝까지 실행하고, 실제 비용이 예약을 넘으면 잔액이 마이너스가 될 수 있다. 잔액이 마이너스면 가용 잔액이 최저 비용보다 작으므로 다음 요청부터 거절된다. 실시간 전사의 구간 재예약(`renew`)도 같은 규칙을 쓴다.
4. **실사용자 환경에서만 강제한다.** `BILLING_ENFORCE=true`는 실사용자 환경(production)의 document-svc에만 켜고, 개발·테스트 환경은 false로 둔다(Fruition-flatform 환경별 설정).

거절은 지금처럼 402 `INSUFFICIENT_CREDIT`이다.

## 대안과 기각 사유

- **A. 가용 잔액이 예상 상한보다 작으면 거절(지금 코드):** 마이너스 깊이가 상한 정도로 제한되지만, 상한은 넉넉하게 잡은 값이라 잔액이 꽤 남아 있어도 막힌다(질의 상한 300원이면 남은 200원으로 질의 불가). 사용자는 "잔액이 있는데 막힌다"고 느낀다.
- **B. 가용 잔액이 0 이하일 때만 거절:** 혼란은 없지만 남은 1원으로도 비싼 요청이 통과한다. 동시에 여러 요청을 보내면 각각 통과해 마이너스가 크게 쌓인다.
- **예약도 최저 비용으로 잡는다:** 동시 요청이 각각 최저만 잡고 모두 통과하므로 B와 같은 문제가 생긴다. 거절 기준(최저)과 예약 금액(상한)을 나눠야 "조금 남아도 쓸 수 있다"와 "동시 요청 과다 지출 방지"를 함께 얻는다.
- **진행 중인 요청을 잔액 소진 시 중단한다:** 이미 공급사에 낸 비용은 돌아오지 않고, 사용자는 결과 없이 비용만 낸다. 마이너스를 허용하고 다음 요청을 막는 편이 낫다(실시간 전사만 구간 재예약 실패 시 연결을 끝낸다).

## 결과

- 사용자는 가장 싼 요청 한 번을 할 수 있는 잔액이 있으면 요청할 수 있다.
- 마이너스는 진행 중인 요청의 실제 비용이 예약을 넘는 만큼만 생긴다. 동시 요청은 앞선 요청들의 예약이 가용 잔액을 채우면 최저 비용 기준에 걸려 거절된다.
- 최저 비용 설정이 실제보다 높으면 A의 혼란이, 낮으면 B의 마이너스 누적이 다시 생긴다. 실제 청구액으로 주기적으로 조정해야 한다.
- 청구가 0으로 새는 호출([ADR-0027](0027-ai-usage-billing-and-price-management.md)의 `unpriced`·`needs_review`)이 남아 있으면 차단의 의미가 줄어든다. 과금 정확성 작업이 먼저 반영돼야 한다.
- 남은 일(#102): `CreditService.reserve`·`renew` 구현과 테스트(잔액 0 / 마이너스 / 최저 미만 / 최저 이상 상한 미만 / 동시 요청), 실사용자 환경 `BILLING_ENFORCE=true`, 402 응답 시 프론트 충전 안내, 마이너스 잔액 처리(다음 충전 상계 등) 문서화.
