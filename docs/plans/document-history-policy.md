# 문서 이력 생성 정책과 revision/version 분리 계획

## 기준과 범위

- 작업 브랜치: `feat/document-history-policy`, 최신 `origin/dev` 기반.
- 우선 작업 범위는 Fruition-document. 프론트 변경이 필요하면 API 계약의 한계를 먼저 구체적으로 기록한다.
- 구현 단계: 저장 정책, 번호 분리, AI 조회/복원 연결, V58 마이그레이션과 검증을 수행한다. 기존 데이터는 삭제하지 않는다.
- 최신 본문 자동저장은 유지한다. 내부 revision은 본문 변경마다 증가하며 충돌 검사의 기준으로 유지한다.
- 일반 이력은 마지막 이력 생성 후 10분이 지났고 마지막 이력과 현재 본문이 다를 때 생성한다. 입력 중지 2분 조건은 적용하지 않는다.
- 승인된 AI 적용 성공은 즉시 이력을 생성한다. 결과가 같은 본문이어도 AI 작업 이력을 생성하되 내부 revision 증가 여부와 기존 no-change 처리를 함께 설계한다.
- 동일 요청 재전송은 새로운 AI 작업으로 취급하지 않는다.
- AI 적용 직전 미기록 본문을 보존하며 기존 AI 비교와 되돌리기는 반드시 유지한다.

## 1. 의존 경로와 API 계약 조사

- DocumentService 저장, 이미지 포함 저장, 문서 생성, 콘텐츠 복원 경로를 조사한다.
- ChangeDiffLoader, AI 복원 계획 및 실행, operation 연결이 revision을 스냅샷 PK로 사용하는 모든 경로를 찾는다.
- 문서 메타데이터 current_version은 편집 revision과 구분하여 유지한다.
- 저장 응답, 목록 current_version, 비교 요청, 복원 base_version의 실제 의미와 프론트 사용을 확인한다.
- 프론트가 하나의 값을 충돌 검사와 화면 이력 번호에 모두 사용하는 경우, 백엔드만으로 잘못된 값을 대신 반환하지 않는다. 추가 revision 필드와 필요한 클라이언트 수정 범위를 명시한다.

## 2. 데이터 모델과 마이그레이션

- document_edit_states.revision은 최신 편집 상태 번호로 유지한다.
- document_content_versions.version은 문서별 이력 번호로 사용하고 revision 컬럼을 추가해 원본 편집 상태를 연결한다.
- 기존 행은 revision=version으로 채우고 기존 version과 operation_id, restored_from_version을 보존한다.
- 기존 이력 번호는 재정렬하지 않고 새 이력부터 마지막 번호+1로 할당한다.
- revision으로 조회하는 인덱스를 추가한다. 동일 revision에 여러 이력이 생길 수 있는 동일 본문 AI 작업의 조회 규칙을 정한다.
- 기록 종류, 기록 기준 시각, 필요 시 AI 적용 전후 역할을 명시한다. 버전 created_at을 본문 수정 시각과 혼용하지 않는다.
- 문서 행 잠금 등으로 번호 할당과 이력 생성을 직렬화한다.

## 3. 저장 및 10분 기록 정책

- 일반 저장은 최신 상태, write receipt, 이미지 참조와 outbox 등 기존 필수 처리를 유지하고 이력 생성을 분리한다.
- 초기 복원 기준 본문을 확보하고 마지막 이력 시각을 설정한다.
- 서버 측 주기 작업으로 미기록 변경 문서를 확인한다. 서버가 멈췄거나 편집 화면을 닫아도 재시작 후 처리할 수 있도록 기준을 DB에 둔다.
- 주기 작업은 문서를 잠근 뒤 경과 시간과 본문 해시를 다시 검사한다. 이미 기록된 내용은 생성하지 않는다.
- AI 적용 및 명시적 복원이 이력을 생성하면 일반 이력 기준 시각도 갱신한다.
- AI 작업은 서버에서 검증한 apply_operation_id를 기준으로 적용 전후 스냅샷과 로그 연결을 원자적으로 처리한다.
- 동일 본문 AI 적용은 기존 no-change 작업 완료 및 복원 가드와 충돌하지 않도록 처리하고, 실제 되돌릴 변경이 없다는 의미를 유지한다.

## 4. 조회, AI 되돌리기, 콘텐츠 복원

- 화면 이력 조회와 diff 대상은 version으로 찾는다.
- AI 로그 beforeRevision/afterRevision은 revision으로 스냅샷을 찾도록 ChangeDiffLoader와 복원 경로를 수정한다.
- 콘텐츠 복원 대상은 version, 저장 충돌 검사는 현재 revision을 사용한다.
- 최신 본문이 마지막 이력보다 앞서 있을 때 현재 표시와 diff의 동작을 명시한다. 목록 조회만으로 새 이력을 만드는 우회는 하지 않는다.
- V57의 restored_from_version 의미와 기존 복원 출처 연결을 유지한다.
- AI 복원과 콘텐츠 복원은 성공 시 즉시 이력을 남기는 경로를 검토한다.

## 5. 검증과 완료 기준

- 10분 미만 일반 편집 및 공백 변경: 본문 저장, 이력 미생성.
- 10분 경계의 미기록 변경: 이력 한 번 생성. 변경 없음: 미생성.
- 6분 뒤 재편집, 편집 중단, 서버 재시작, 다중 주기 작업의 정책과 중복 방지.
- 일반 편집→AI 적용→일반 편집→AI 되돌리기, 연속 AI 적용, 기존 AI 로그의 비교·복원.
- 동일 본문 AI 적용, 재전송, 실패, 동시 저장와 주기 작업 경쟁.
- 이미지 포함 저장, 과거 이미지 참조/정리, 콘텐츠 복원과 restored_from_version.
- 마이그레이션 전후 기존 이력 및 AI 연결 보존.
- 의미 있는 단위/통합 테스트와 필요한 백엔드 전체 검사 실행. API 명세 및 변경 문서 갱신.
- 프론트 무수정 호환 여부를 검증하고, 불가능한 경우 필요한 최소 계약 변경을 구체적으로 보고한다.

## 주요 리스크

- revision과 version의 혼용으로 AI diff/복원이 잘못된 본문을 조회할 위험.
- 현재 이력 표시와 복원 base 값이 하나의 번호를 전제로 하는 API/프론트 계약.
- 동일 본문 AI 작업은 revision과 이력 번호가 일대일이 아닐 수 있음.
- 일반 이력은 10분 사이의 모든 편집 상태를 보존하지 않는다. 공백 변경도 10분 시점에 이력과 다르면 기록한다.
- 이력 주기 작업과 저장 경쟁으로 중복 또는 누락될 위험.

기존 미커밋 작업과 기존 이력 데이터는 이 작업에서 삭제하거나 덮어쓰지 않는다.
